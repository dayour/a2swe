## sdk-boundary

**Decision:** No. Agent 365 does not replace the Microsoft 365 Agents SDK, and the Agent 365 SDK does not host your existing agent.

- **A365-C03:** The SDKs are complementary. The Microsoft 365 Agents SDK remains the conversational-agent framework, while Agent 365 adds enterprise capabilities. Sources: [Microsoft Agent 365 SDK and CLI](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/), heading **“How is the Agent 365 SDK different?”**; [Microsoft Agent 365 SDK overview](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk), heading **“Compare Microsoft Agent 365 SDK and Microsoft 365 Agents SDK.”**
- **A365-C02:** The Agent 365 SDK extends existing agent logic, framework, and hosting; it does not build, host, deploy, orchestrate, or execute the agent. Source: [Microsoft Agent 365 SDK overview](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk), heading **“What it is and what it isn't.”**

**Engineering rationale:** Keep the current framework and hosting model. Adopt only the Agent 365 capabilities needed for identity, observability, tools, or notifications. This is guidance only; no hosting or SDK changes were executed.

## telemetry-diagnosis

**Diagnosis:** HTTP 200 alone does not prove that spans were accepted, associated with the correct agent, or exposed in Agent 365 surfaces.

1. **Verify assigned licensing.** At least one user must actually be assigned Agent 365 or Microsoft 365 E7; possessing only a tenant SKU is insufficient. **A365-C12:** [Connect an existing agent to Agent 365](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/get-started), heading **“Prerequisites”**; [Agent 365 observability concepts](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts), heading **“Limits and drop conditions.”**
2. **Verify authorization without sharing credentials.** Confirm the intended identity mode, required ingestion permission, the identity to which it is assigned, and administrator consent. Declaring a permission does not grant it. **A365-C17:** [Agent 365 identity](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity), heading **“Permissions and runtime flow.”** Use redacted app IDs, permission names, consent status, and error metadata—not tokens or secrets.
3. **Verify direct-ingestion identity binding.** For direct OTel ingestion, the route agent ID and `gen_ai.agent.id` must equal the authenticated agent **appId**, not an Entra object ID or blueprint appId. **A365-C13:** [Agent 365 observability concepts](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts), heading **“Agent identity is bound to the URL.”**
4. **Verify trace shape and correlation.** The principal agent-activity surfaces require a valid `invoke_agent` root, with inference and tool spans correlated beneath it. Missing the root does not prove every child span was lost; child spans may remain queryable through Defender advanced hunting. **A365-C11:** [Connect an existing agent to Agent 365](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/get-started), heading **“Instrument for observability”**; [Agent 365 observability concepts](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts), heading **“Where Agent 365 observability data appears.”**
5. **Record per-span outcomes.** For one known trace, record each root, inference, and tool span’s trace/span ID and acceptance or rejection result. Do not treat a batch-level HTTP 200 as proof that every span passed validation.
6. **Verify downstream visibility separately.** Check the expected Agent 365 surface and, where applicable, Defender advanced hunting. Successful transport, accepted ingestion, and product visibility are distinct acceptance stages.
7. **Preserve working instrumentation while diagnosing.** For a new integration, Microsoft OpenTelemetry Distro is recommended; the earlier Observability SDK remains supported. **A365-C10:** [Agent 365 observability concepts](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts), heading **“Pick your integration path.”**

**Execution:** This is a proposed diagnostic sequence. No exporter, trace payload, permission assignment, license, or downstream telemetry was inspected.

## identity-boundary

**Decision:** Do not silently switch from S2S to delegated access. That would change the security and consent model, not merely repair a permission error.

- **A365-C07:** S2S acts as the agent without human context; OBO acts for a signed-in user; Agentic-User acts as the agent’s own account. Source: [Agent 365 identity](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity), heading **“Permissions and runtime flow.”**
- **A365-C17:** Declaring permissions does not grant them; administrator consent is required where applicable. Source: [Agent 365 identity](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity), heading **“Permissions and runtime flow.”**

**Proposal:** Keep S2S and verify whether the downstream operation supports application permissions, whether the correct permission is assigned to the agent identity, and whether consent was completed. If the operation only supports delegated access, explicitly redesign it as OBO with sign-in, consent, authorization review, and updated tests. No identity mode or permission was changed.
