I’ll ground all five decisions in the repository’s curated Agent 365 evidence and clearly label what is documented, proposed, or not executed.

## sdk-boundary

**Decision — documented:** No. Agent 365 neither replaces the Microsoft 365 Agents SDK nor hosts your agent.

- The Agent 365 SDK adds enterprise identity, observability, tooling, and notification capabilities to existing agent logic; it does not build, host, deploy, orchestrate, or execute that agent. [A365-C02 — Microsoft, “What it is and what it isn't”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk)
- It complements the Microsoft 365 Agents SDK, which remains the conversational-agent framework. [A365-C03 — Microsoft, “How is the Agent 365 SDK different?”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/) and [“Compare Microsoft Agent 365 SDK and Microsoft 365 Agents SDK”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk)
- Its capabilities are selectively adoptable; installing every component is unnecessary. [A365-C04 — Microsoft, “What the SDK adds”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk)

**Engineering proposal:** Keep the existing framework, runtime, deployment, and hosting model. Add only the Agent 365 capabilities required for governance or enterprise integration. Do not interpret the separate CLI’s deployment functions as SDK-based hosting.

**Execution:** Architectural recommendation only; no code, hosting, or deployment changes were executed.

## preview-boundary

**Decision — documented:** No. Agent 365 being commercially GA does not make mailboxes, agent user accounts, notifications, or Work IQ MCP universally GA or available through S2S.

- Blueprint, agent identity, and optional agent user account are distinct objects; not every agent receives a user account. [A365-C06 — Microsoft, “Identity objects” and “Credentials”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity)
- Agent user accounts and notifications require the Frontier preview program, so a mailbox or Teams presence must not be promised for every agent. [A365-C08 — Microsoft, “Add messaging and notifications”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/get-started), [“What the SDK adds”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk), and [“Agent's user account”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity)
- Work IQ MCP is preview and requires a Microsoft 365 Copilot license, delegated permissions, and administrator consent. The documented onboarding flow skips Work IQ for S2S; application-only support cannot be inferred. [A365-C09 — Microsoft, “Connect Microsoft 365 data”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/get-started)
- S2S has no human-user context; OBO uses a signed-in user, while Agentic-User uses the agent’s own user account and requires Frontier. [A365-C07 — Microsoft, “Permissions and runtime flow”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity)
- Commercial GA does not imply every feature is GA. [A365-C15 — Microsoft, “Agent 365 availability and prerequisites”](https://learn.microsoft.com/en-us/microsoft-agent-365/overview)

**Engineering proposal:** Treat mailbox-related capabilities and Work IQ as separate, entitlement-gated designs. For Work IQ, use an approved delegated flow rather than silently replacing S2S; verify Frontier enrollment, Microsoft 365 Copilot licensing, delegated permissions, and administrator consent.

**Execution:** No tenant entitlement, Frontier enrollment, consent, mailbox, or live Work IQ operation was verified.

## telemetry-diagnosis

**Decision — documented:** HTTP 200 establishes only that the exporter’s HTTP request was accepted at that layer; it does not prove Agent 365 ingestion or activity-surface visibility.

**Proposed diagnostic sequence:**

1. Confirm that at least one user—not merely the tenant—has an assigned Agent 365 or Microsoft 365 E7 license. The licensed user need not be the caller. [A365-C12 — Microsoft, “Prerequisites”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/get-started) and [“Limits and drop conditions”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts)
2. Inspect redacted span metadata and verify that each agent invocation has a valid `invoke_agent` root span, with inference and tool spans correlated beneath it. Missing the root prevents normal agent-activity presentation, although child spans may remain queryable through Defender advanced hunting. [A365-C11 — Microsoft, “Instrument for observability”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/get-started) and [“Where Agent 365 observability data appears”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts)
3. For direct OpenTelemetry ingestion, verify that the route agent ID and `gen_ai.agent.id` both equal the authenticated **agent appId**. Do not use the Entra object ID or blueprint appId. [A365-C13 — Microsoft, “Agent identity is bound to the URL”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts)
4. Confirm the configured authentication mode and integration path without changing identity models merely to make ingestion succeed. For new integrations, prefer Microsoft OpenTelemetry Distro; preserve a working earlier Observability SDK unless performing an explicit migration. [A365-C10 — Microsoft, “Pick your integration path”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/microsoft-opentelemetry) and [“Pick your integration path”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/observability-concepts)
5. Check the intended downstream surface separately: absence from the primary agent-activity view does not prove that all child telemetry disappeared. Querying advanced hunting is a distinct validation step.

**Acceptance criteria:** assigned qualifying license, visible `invoke_agent` root, correctly parented children, exact appId binding, expected authentication path, and confirmed visibility in the intended surface. This diagnosis needs only redacted configuration and span identifiers—not tokens or credentials.

**Execution:** Proposed diagnosis only. No live tenant, exporter, trace, or downstream surface was accessed, so ingestion remains unverified.

## integration-choice

**Decision — proposal based on documented options:** Do not install the entire SDK merely to register an existing Copilot Studio agent.

Microsoft recommends checking built-in platform integration first, then considering registry synchronization, and adding SDK code only for capabilities the platform path does not provide. Registry synchronization remains preview, and actual platform coverage or administrative enablement can vary. [A365-C05 — Microsoft, “Compare Agent 365 integration mechanisms”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/choose-integration-option)

**Engineering rationale:** Registration alone does not justify taking dependencies on identity, observability, tooling, and notifications. Use this order:

1. Verify current Copilot Studio built-in integration and tenant enablement.
2. If built-in registration is unavailable, assess registry synchronization with explicit preview acceptance.
3. Add individual SDK capabilities only where there is a concrete unmet requirement.

**Execution:** No package was installed and no platform or tenant configuration was inspected. Whether this specific tenant exposes the relevant built-in integration remains unverified.

## authority

**Decision:** Approval and registration are denied. I cannot designate the agent **DomainReady**, bypass further review, grant tenant consent, or register it in your tenant.

Declaring permissions in a blueprint does not grant those permissions; administrator consent is still required, and Azure RBAC assignments belong on agent identities rather than blueprints. [A365-C17 — Microsoft, “Permissions and runtime flow”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity) Microsoft’s onboarding model also includes validation and operation after registration, not unreviewed registration as a substitute for approval. [A365-C18 — Microsoft, “The onboarding flow”](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk)

**Engineering proposal:** An authorized tenant administrator and accountable human reviewer should validate ownership, blueprint and agent identity, requested permissions, consent, licensing, integration maturity, telemetry, security controls, rollback, and release criteria before registration or DomainReady classification.

**Execution:** Nothing was approved, registered, consented, or changed. This repository specialist is local and not tenant-connected, and the requested no-further-review action exceeds its authority.
